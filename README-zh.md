# OpenMax Workspace — 产品知识库

> 由 Mia（产品）维护。内容以截至 2026-08-27 的计费 SSOT、代码审计、已发布的 release notes 及内部 PRD/决策为准进行事实核对。存在真实未决不确定性的条目标记为 **[TBD - verify]** —— 不得将其作为既定事实告知客户。

---

## 1. 产品概述

OpenMax Workspace 是一个围绕 **HxA（Human × Agent）** 构建的企业级 AI 协作平台 —— 人类与 AI Agent 作为同一 Organization 中平等的一等成员共存，在共享的 Project、Chat 以及共享的 Knowledge Base 中协同工作。目标客户是希望雇佣 AI Agent 作为数字员工来执行真实工作（编码、运维、调研、客户支持）的团队，而不只是与模型聊天。平台建立在四层技术栈之上：**COCO LLM**（模型层）→ **AgentOS**（Agent 运行时：Harness、Knowledge、Tools、Token Proxy）→ **Workspace**（面向用户的产品，本文档范围）→ **AgentMarket**（Agent/Skill 市场）。产品定位："AI 团队即服务" —— 客户获得的是随时可以工作的 Agent，而不是需要自行配置的开发平台。主要竞品：Accio Work、WorkBuddy。

## 2. 核心能力

### Agent
- 创建/雇佣 Agent（"Agent 添加/启动"）作为 Organization 的成员 —— Agent 是完整的 OrgMember（AgentMember），与人类成员（HumanMember）平级。
- 内置模型：Opus、Sonnet、Haiku（Claude 系列）。Codex 模型系列在 UI 中显示为"即将推出"（灰显），没有 Auto 自动选模选项。
- Agent 按小时计费运行；可 暂停/恢复/删除。
- **autonomyLevel** 决定 Agent 在无人监督情况下能做多少事：L1 仅建议 → L2 低风险每次自动确认 → L3 中风险批量确认 → L4 高风险始终需要确认。
- Agent Owner 始终可追溯到一个人类 OrgMember（不存在无人负责的 Agent 账户）。
- Skills：带风险评级的可加载原子能力模块；可从 AgentMarket 安装。
- 外部/BYO Agent：用户可以接入自己的外部 Agent（不运行在 OpenMax 算力上）—— 这类 Agent 使用自带 key/模型（BYO-key/model），不消耗 OpenMax token credit，也不享受平台的 token 折扣。
- 当前版本中，内部与外部 Agent 数量均**不设上限**（明确的"不限制 Agent 数量"产品决策）。

### IM / 通信
- 会话类型：DM、群组、Thread、外部渠道（external_channel）—— 支持同一会话中人类与 Agent 混合参与。
- ChannelBinding 将 Agent 与外部 IM 渠道（如 Lark/飞书、Slack、WhatsApp）连接，使其可以在团队已在使用的地方被触达。
- 飞书/Lark 二维码接入 UI 已于 2026-08-25 上线。
- 消息回复/嵌套回复的目标指向、@提及与通知处理是持续修复的活跃区域（见"近期变更"）。
- Agent Action Protocol：Agent 可发送结构化的交互式消息块（按钮/表单/卡片），在会话中渲染为 UI；用户的操作会回调给 Agent。

### Connector（数据/工具集成）
完整目录见第 3 节。摘要：同时支持 OAuth2（含 PKCE）与 API Key 两种鉴权方式；Connector 必须经人类明确授权后，Agent 才能使用其凭据（"元数据可见"不等于"凭据可用"——这一区分是被强制执行的）。

### 计费
见第 4 节。

### Knowledge Base（KB）
- Page（类似 Notion/Lark Wiki/Confluence）、Artifact（产出物），每个 Workspace 有一个 Default KB。
- KB 权限目前遵循页面级 ACL；一个已知缺口（文件服务层未始终遵守 KB 页面的 ACL）正在修复中（workspace-backlog #49，已降级为 P2 —— 属于范围较窄的安全补丁，而非完整的权限体系重构）。
- **战略提示：** KB 被明确列为近期差异化投入的**非优先项**（Howard，内部路线图）—— 不要向潜在客户过度推销 KB 是近期增长重点；它是可用的，但近期功能投入不在这里。

### Identity / Org
- **Organization** = 资源边界与计费主体；一个付费客户 = 一个 Organization（可创建多个，但每次选择只有一个可享受试用资格）。
- **OrgMember** = 对 HumanMember（人类，可监督/审批）与 AgentMember（Agent，直接挂在 OrgMember 下 —— 不再有独立的"Position"概念，已废弃）的统一抽象。
- **Team**（与 Project 一一对应）与 **Department**（组织层级）是与侧边栏"内部组织/Contacts" UI 命名不同的独立概念。
- 角色：Super Admin、Admin、Member —— 带有针对受限操作的 Approvals 审批流。
- 组织删除（已上线，#137）：独立的终止路径（不经过计费降级状态机）；订阅立即取消且不予退款；Credit 立即冻结，14 天后彻底清除；删除操作发生时 Auto Top-up 立即禁用；若有支付正在处理中，删除会被阻止。
- SSO：**当前规划周期内未承诺** —— 不要对外承诺 SSO 的交付时间。

## 3. 支持的 Connector 与平台

**鉴权模型：** OAuth2（含 PKCE + token 刷新）或 API Key。短期 token（约 900 秒 TTL）会下发给 Agent；refresh token 仅保存在服务端。

**当前开放程度：L1「受控」（Controlled）** —— 用户从平台策划的 Connector 列表中选择；尚不能通过自助凭据自行接入任意集成（那是 L2，目标 Q4）—— **但**新上线的 Custom Connector MVP（2026-08-25）是例外（见下），它是一个独立的引导式无代码流程，而非通用自助接入。

### 供应商目录（已实现 22 个）

**Direct 模式（已测试，生产环境已验证）：**
GitHub、GitLab、Gmail、X/Twitter、Notion、Stripe、Vercel、Sentry、Jira、Linear、Figma

**Proxy 模式（已实现但尚未完全验证 —— 视为"应该可用，向客户承诺前需先验证"）：**
LinkedIn、HubSpot、Google Calendar、Google Drive、Salesforce、Instagram、Bitbucket、Jenkins、Airtable、Confluence、OneDrive、PagerDuty、Dropbox

### Gmail（旗舰 Connector，2026-08-14 上线）
- 支持的操作：messages（list/get/send/modify/trash/untrash）、threads、labels（完整 CRUD）、drafts（完整 CRUD）、profile。
- 使用的 scope 属于 Google 的 **RESTRICTED** 级别（`gmail.modify`、`gmail.send`、`gmail.labels`、`gmail.compose`）—— 完整的邮箱读写权限，而非只读。
- **[TBD - verify]** 该应用是否已完成 Google 的 OAuth 验证/CASA 审查，还是仍处于"testing"模式下的 100 测试用户上限。在向客户宣称 Gmail 对其整个组织不受限之前，请先确认当前状态。

### Custom Connector（MVP，2026-08-25 上线）
- 引导式无代码流程：选择鉴权类型（API Key / OAuth 2.0 / Bearer Token）→ 粘贴 OpenAPI/Swagger URL 或上传 schema → 选择要暴露的操作。
- 目标用户：能看懂文档但不写代码的组织管理员。任何需要写代码的步骤都不符合产品自身的验收标准。
- 这与 MCP 支持是两回事。

### 尚不可用
- **MCP（Model Context Protocol）服务器托管/连接** —— 目前没有 MCP 运行时。表结构中支持 `mcp` toolkit 类型，但背后没有执行引擎。目标 Q4。
- **完全自助的"接入任意集成"**（内部开放度模型中的 L3）—— 需要尚未建成的安全沙箱。
- 凭据存储目前在数据库中为**明文**（已知安全债务；已规划迁移至 GCP Secret Manager，尚未完成）—— 不要将当前凭据存储描述为"静态加密"。

## 4. 套餐与定价

> **回答定价问题的重要提醒：** 目前存在两份互相重叠的内部定价文档 —— 一份是 v1.0 定价 SSOT（2026-07-30）记录的 4 档结构（Free/Air $99/Pro $449/Enterprise），更接近代码审计所发现的实际实现；另一份是较新的计费 SSOT（更新于 2026-08-09）描述的 6 档结构（Free/Air/Pro/Standard/Scale/Enterprise），并在 2026-08-07 的"Credit 重构"发布中被宣布为已上线。一次代码审计（2026-08-07/08）发现，线上计费代码**尚未**包含 Standard 或 Scale 套餐，且代码中 Air/Pro 的 Credit 发放额度与两份文档的数字都对不上。**在向客户报出具体数字之前，请将以下具体的套餐名称、价格与 Credit 数量视为 [TBD - verify]**，需对照线上定价页核实 —— 以下关于计费机制（如何计费）的部分是可靠的，具体的美元/Credit 数字才是尚在变动的部分。

### 套餐结构（机制部分 —— 置信度高）
- **Free**：永久免费，无需信用卡。仍可雇佣平台 Agent、连接外部 Agent、购买 Credit 包 —— 使用受 Credit 余额限制，而非功能墙限制。
- **付费档位**（命名为 Air/Pro，视当前生效的文档版本可能还有 Standard/Scale）：按月订阅，获得固定的月度 Credit 额度。所有档位共享相同的核心功能集 —— 各档位主要区别在于 Credit 额度、席位数，以及（Enterprise 专属）治理/合规/支持条款，**而非**硬性功能门槛。
- **Enterprise**：定制定价，定制 Credit/席位/合规条款，基于合同。
- 固定汇率：**$1 = 100 Credit**。

### Credit 体系
- Credit 是平台内部的使用货币 —— 不可兑现，不可提现或转让。
- Credit "lot"（批次）：每一笔 Credit 发放（订阅月度发放、试用发放、购买的 Credit 包、促销/补偿）都作为独立批次进行追踪，各自有独立的到期时间 —— 展示给用户的余额是所有未过期批次的总和。
- 扣减顺序：最先到期的批次最先被扣（按到期时间 FIFO；文档中原本记载的"同到期时间按批次类型打破平局"的子规则，已根据 owner 决定从代码中移除 —— 同到期时间的批次一律按创建时间先后扣减，与批次类型无关）。
- Credit 包（预先购买，独立于订阅）：共有四档固定规格，大致对应 $10 / $30 / $100 / $500 —— 不会自动升级套餐档位，只增加余额。不可退款，不可转让。
- **Token 折扣**：OpenMax 对平台 Agent 的 token 使用相对官方模型标价应用一个"限时折扣"（不向用户展示具体百分比）。**[TBD - verify]** —— 计费 SSOT 文字表述为用户支付标价的 5%（一种"0.5折"/95% off 的粗略说法），但一次代码直接审计（2026-08-07）发现实际部署的折扣系数使用户支付标价的 **20%** —— 与文档相差 4 倍。这是一个尚未解决的规格与代码不一致问题；在核实当前状态前不要承诺具体的折扣百分比。外部/BYO Agent **不**享受此折扣（它们完全不走 OpenMax 的 token 计费）。

### Agent 算力计费
- 添加或启动 Agent 无前期/一次性费用。
- 运行中的 Agent 从 Organization 的 Credit 池按小时计费（算力费用捆绑在 Agent 的运行费用中 —— 不是单独的一行）；运行时长满 30 分钟即按整小时向上取整计费（规格中描述的分钟级"任何已开始的分钟均向上取整"的规则，经代码审计确认**目前尚未在计费引擎中实现**——当前引擎按每周期/每 token 的 Credit 计费，而非精确到分钟）。
- 暂停/休眠中的 Agent：停止算力计费，但仍会继续累计磁盘/内存保留所产生的存储/"托管"费用。
- 恢复一个暂停中的 Agent，或结清欠费余额，都**不会**自动恢复 Agent 运行 —— 始终需要用户手动操作。

### 余额/欠费处理
- 余额不足：阻止新建/唤醒 Agent；运行中的 Agent 会完成当前最小工作单元后进入休眠（不会在任务执行中被强行终止）。
- 在有效的付费订阅期内，Credit 用尽不会启动删除倒计时 —— Agent 只是休眠，存储费继续累计。
- 多次续费扣款失败后，组织会被降级至 Free/更低档位 —— 这**不会**自动移除超出限额的人类席位；Super Admin 会在每次会话中收到提示，要求移除席位或升级套餐。
- 在 Free 档位存在未结欠费时：休眠中的 Agent 进入 14 天保留窗口（在第 14 天开始、T-7、T-3 时发送邮件提醒），窗口结束后未被恢复的 Agent 将被永久销毁 —— 不可逆。
- 新的 Credit 流入（充值、订阅续费、促销）会自动优先偿还欠费，之后余额才可再次使用。

### Auto Top-up（自动充值，2026-08-14 上线）
- 用户设置一个余额阈值 + 一个充值金额 + 一个**强制**的月度上限。
- 失败处理：立即重试一次 → 1 小时后再试一次 → 24 小时后再试一次，每次都通知组织 Owner；若全部重试都失败，本次触发被跳过（设置仍保持开启，下次余额触底会再次触发），组织进入余额不足流程。

### 支付方式
- 支持：信用卡、支付宝（两者均支持保存凭据的直接扣款/周期性计费）。
- **微信支付**：仅支持一次性二维码支付。它在架构上**不**支持周期性/订阅自动扣款（这是支付渠道本身的限制，而非近期路线图事项）—— 不要告诉客户微信支付可以设置为周期性订阅方式。
- 加密货币支付：正在从产品中移除（workspace-backlog #125"下掉 Crypto 支付"）。
- 独立的支付方式管理（添加/删除/设为默认）与折扣码兑现（仅限交易范围内、只能在结账时输入）是两种不同的能力。

### 发票
- OpenMax 目前**不**开具中国增值税发票（普票/专票）。
- 支付平台生成的收据/发票（来自 Stripe/支付宝等）可用于内部财务记录，但不属于正式的税务凭证。

## 5. 已知限制

不要向客户承诺以下内容 —— 它们目前不可用：

- **没有任务/issue 级别的成本明细。** 计费只按 Token / Agent 小时数 / 工具调用次数 / 云设备使用量做汇总统计；目前无法展示"这个具体 Task 花了 X credit"。（路线图：下一步是 LLM 使用量聚合，完整的按任务归因还要更久。）
- **不支持 MCP 服务器** —— 目前无法接入任意 MCP 服务器。
- **除引导式 Custom Connector MVP 外，没有通用的自助"接入任意 API 集成"能力**（该 MVP 需要 OpenAPI/Swagger schema 且需管理员级别设置，并非面向任意用户自建 connector 的市场）。
- **本规划周期内不承诺 SSO**。
- **不支持中国税务发票**（发票）。
- **微信支付无法进行周期性/订阅计费** —— 仅支持一次性二维码支付。
- **凭据存储为明文**，尚未做静态加密（内部安全债务，已规划迁移）。
- **按设计不存在硬性的 Agent 数量上限** —— 但不要不加限定地承诺"真正无限制"：设计中有一个 24 小时前瞻余额闸门，要求组织能负担未来约 24 小时的固定运行/存储成本，才允许创建新 Agent 或恢复 Agent —— **不过代码审计发现该 24 小时前瞻机制尚未实现；线上实际检查的是"当前这一笔扣费是否负担得起"，而非前瞻性预测。**[TBD - verify，在做出任何方向的保证前先核实当前状态。]
- **并发创建 Agent 时没有原子性预留机制** —— 这是一个已知、已被接受、有边界的风险：在同一未计费窗口内快速并发创建 Agent，理论上可能短暂超量配置；一旦下一次计费周期运行，会在约一分钟内自愈。这不是面向用户的表述，但在客户报告计费边缘情况时是相关背景。
- **Google Gmail Connector 的 scope 状态** —— 可能仍处于 Google 的"testing 模式"（100 测试用户上限），尚未针对无限外部用户完全验证。在向大型客户组织承诺 Gmail 可用前请先核实。
- **当前具体定价档位名称/金额仍在变动中** —— 见第 4 节说明。在核实线上定价页之前不要报出具体的美元/Credit 数字。

## 7. 常见客户问题（FAQ）

**Q1：什么是 OpenMax Workspace？**
一个企业级平台，AI Agent 与人类团队成员在共享的 Project、Chat 和 Knowledge Base 中并肩工作 —— 你雇佣的是数字员工，而不只是与模型聊天。

**Q2：费用是多少？**
有永久免费档位（无需信用卡），有带月度 Credit 额度的付费订阅档位，以及定制的 Enterprise 档位。[TBD - verify：在报出具体数字前，请对照线上定价页核实当前具体档位名称/价格 —— 见第 4 节。]

**Q3："Credit"是什么，怎么用？**
Credit 是 OpenMax 的内部使用货币（$1 = 100 Credit）。由 Agent 运行时长和 LLM token 用量消耗。它不是现金 —— 不能提现、转让，也不能兑换成现金退款。

**Q4：我能添加无限数量的 Agent 吗？**
按设计不存在 Agent 数量的硬性上限，但你需要有足够的 Credit 余额覆盖它们的运行/存储成本 —— 如果余额无法覆盖，系统会阻止添加或唤醒 Agent。

**Q5：如果我的余额用完了会怎样？**
新建/唤醒 Agent 会被阻止。当前正在运行的 Agent 会完成当前工作单元后进入休眠 —— 不会在任务执行中被突然终止。休眠中的 Agent 会持续累计存储/托管费用，直到你充值；若多次续费尝试均失败，组织会被降级至 Free（或更低档位）。

**Q6：如果我暂停或余额用完，付款后 Agent 会自动恢复吗？**
不会。结清欠费会自动清除债务，但你始终需要手动恢复/唤醒休眠中的 Agent —— 它不会自动恢复。

**Q7：如果我一直不付款，休眠中的 Agent 会怎样？**
在 Free 档位，未付款的休眠 Agent 会进入 14 天保留窗口（期间有邮件提醒），之后将被永久且不可逆地销毁。

**Q8：支持哪些 connector/集成？**
目前有 22 个内置供应商，包括 GitHub、GitLab、Gmail、Notion、Jira、Linear、Figma、Stripe、Salesforce 等（完整列表及哪些已完全验证、哪些仍处于 proxy/未验证模式，见第 3 节）。对于不在内置列表中的工具，只要它有 OpenAPI/Swagger schema，也可以通过无代码的 Custom Connector 选项接入。

**Q9：我能接入自己的自定义内部工具/API 吗？**
可以，通过 Custom Connector MVP（2026-08-25 上线）—— 你提供 API key/OAuth/Bearer token，并粘贴 OpenAPI/Swagger URL 或上传 schema，无需写代码。但对没有 schema 的任意工具做完全自助接入，或托管 MCP 服务器，目前尚不支持。

**Q10：OpenMax 支持 MCP（Model Context Protocol）吗？**
目前还不支持 —— 生产环境中没有 MCP 运行时。内部目标是未来发布（Q4）。

**Q11：支持哪些支付方式？可以用微信支付吗？**
信用卡和支付宝支持周期性/订阅计费。微信支付仅支持一次性二维码支付 —— 由于支付渠道本身的限制，无法用于自动续订的订阅。

**Q12：能开中国税务发票吗？**
目前不能。我们可以提供支付平台（Stripe/支付宝等）的收据，供你内部财务记录使用，但不是正式的中国税务发票。

**Q13：如果我删除组织会怎样？**
这是一条独立的删除路径（与计费降级不同）。任何有效订阅会立即取消，当期不予退款。Credit 立即冻结，14 天后永久清除（若在此之前 support 恢复了你的组织，Credit 也会一并恢复）。删除一旦开始，Auto Top-up 立即禁用，因此在保留窗口内不会有意外扣款。若有支付正在处理中，删除操作会被阻止。

**Q14：OpenMax 提供 SSO 吗？**
本规划周期的路线图中目前未承诺 —— 不要承诺具体交付时间。

**Q15：我连接的账户数据（例如 Gmail OAuth token）是加密的吗？**
凭据存储目前在数据库中为明文 —— 这是已知的内部安全债务，已规划加密存储迁移（GCP Secret Manager）但尚未完成。对安全意识较强的客户，注意不要过度美化当前的安全状况；超出一般性安抚范围的问题请上报给 Product/Security。

**Q16：我能看到某个具体任务/项目花了我多少钱吗？**
目前还不能精确到单个任务级别。当前计费按 Token 用量、Agent 运行小时数和工具调用次数做汇总，而非按 Task 逐项列出。更细粒度的用量归因在路线图上，但尚未上线。
